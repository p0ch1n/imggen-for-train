1.背景與問題

目前上線的物件偵測模型，是以 COCO 資料集訓練出的通用模型（person、car 等通用類別）， 部署在實際的 CCTV 即時監控場景中運作。上線後觀察到兩類錯誤：

  • 誤判（False Positive）：場景中的草地土堆、石頭、樹樁、暗影等「長得像人/車」的物體被誤判為目標類別。
  • 漏偵測（False Negative）：夜間、雨霧、低解析度等真實攝影機條件下，目標物偵測不到。

標準解法是蒐集更多真實場景資料重新標註訓練，但訓練模型所在的環境被限制、不能對外蒐集新資料 （沒有網路存取、無法匯入新的現場影像），因此退而求其次：用生成式影像模型在既有的 COCO 影像基礎上 「合成」出像誤判/漏偵測場景的訓練資料，看能不能在不違反資料限制的前提下改善模型。

2.方法原理

核心想法分兩條路線，分別對應上面兩種錯誤：

A. 降低誤判 → 合成「難負樣本」

用 Qwen-Image（文字生成影像）直接生成「長得像人/車但其實不是」的場景 （土堆、石頭、樹樁、垃圾袋、帳篷防水布⋯），標成「背景、無目標物」。 另外用 Qwen-Image-Edit 把既有 COCO 影像裡的人「去除」，生成去掉人之後的配對負樣本（背景保持不變）。 讓模型看過夠多「像人但不是人」的樣本，降低對這些混淆物的誤判。

B. 降低漏偵測 → 保標籤的風格轉換

用 Qwen-Image-Edit 對同一張已標註的 COCO 影像做風格轉換（夜視、雨天、起霧、低解析度 CCTV 畫質⋯）， 要求物體位置、大小、姿勢完全不變，因此原本的標註框可以直接沿用。 讓模型在惡劣條件下也看過同樣的目標物長相，改善夜間/雨霧下的漏偵測。

但生成模型不可靠——可能把人也一起生成進「負樣本」、可能在編輯時把物體移位或消失、可能產生幻覺物件。 所以整條流程設計了自動品質把關機制：用另一個獨立的「teacher 偵測模型」檢查生成結果， 加上不需要模型的「結構相似度」比對（確認編輯前後除了要求的改變之外，畫面結構沒有跑掉）， 雙重過濾掉不合格的生成圖，不合格就直接丟棄，不依賴人工全部看過一遍。

最後，不是「生成資料 = 有效」就直接上線，而是用對照實驗驗證：把新資料加進訓練集、與「只延長訓練時間但資料不變」 的對照組比較，用真實部署畫面（而非合成資料）當作評估基準，統計上顯著才算數，避免把生成資料的「幻覺改善」誤認成真的進步。

3.專案架構與流程

syngen_od/ 專案把整個流程拆成 16 個可重入（resumable）、可分片（multi-GPU shard）的腳本：

坑 1：gcsfuse 上用 mmap 讀模型權重極慢

/home/kasm-user/Personal_Data 是掛在 gcsfuse（GCS 網路硬碟）上的。diffusers 讀 .safetensors 預設用 mmap，在 gcsfuse 上會變成大量隨機小區塊讀取： 實測讀取速度只有約 0.9 MB/s，2.5GB 的模型要讀 近 50 分鐘才會載入完成。

對照：把同一份模型用 cp -r 整包循序複製到本機磁碟，2.5GB 只花了 21.5 秒 （約 116 MB/s）。結論：任何要被模型讀取的權重檔，一律先搬到非 gcsfuse 的本機路徑，再做推論； 純粹的大檔案循序搬移走 gcsfuse 沒問題，問題出在推論時的隨機讀取模式。

坑 2：Python venv 也不能建在 gcsfuse 上

在 Personal_Data 底下建 venv / pip install 涉及大量小檔案的建立與刪除， 同樣會被 gcsfuse 拖慢到幾乎卡死（一個 rm -rf venv 跑了 10 分鐘以上都刪不完）。 改到本機路徑 /home/kasm-user/.venvs/syngen_od 建立後，秒建秒裝。

坑 3：torch / torchvision 版本需要同一個 index 來源

一開始把整個 pip install 指令都指定 --index-url .../whl/cpu， 結果連 pyyaml 這種純 Python 套件也只能在 PyTorch 的 CPU wheel 索引裡找，裝不到而失敗 ——該 index 只拆成 torch 單獨裝，其餘套件走預設 PyPI。 之後裝 ultralytics 時，它又自動帶入一個跟現有 torch build 不匹配的 torchvision （ABI 不合，operator torchvision::nms does not exist），改成重新從同一個 CPU index 裝 torchvision 才解決。

最終環境：torch 2.14.1+cpu、diffusers 0.41.0、transformers 5.19.0、 torchvision 0.29.1+cpu、ultralytics 8.4.177。

本機測試用的設定檔

新增 configs/local_cpu.yaml（獨立設定檔，刻意不用 extends: pipeline.yaml， 因為 sd-turbo 的 pipeline 不接受 Qwen 專用的 true_cfg_scale 參數）：

6.2　CCTV 真實感後處理：OSD 浮水印 / 暈影 / 魚眼廣角

真實的 CCTV/NVR 畫面幾乎都有三個生成模型很難穩定畫出來的特徵，所以改用確定性的影像後處理而不是 要求 Qwen-Image 畫出來（要求擴散模型畫出清晰、固定位置的小字時間戳記非常不可靠）：

效果做法安全性（對已標註的框）
osd_overlay — 浮水印時間戳記 右下角畫出 CAM-xx YYYY-MM-DD HH:MM:SS（黑底白字），模擬 NVR 疊字 安全 只覆蓋角落一小塊，不移動其他內容的座標
vignette — 暈影 邊角亮度衰減，模擬廣角鏡頭的暗角 安全 純亮度調整，不移動像素位置
barrel_distort — 魚眼/桶狀畸變 除法模型 r_src = r_out / (1+k·r_out²) 的最近鄰重新取樣，模擬半球型廣角鏡頭 僅限無框任務 會搬動像素位置，若不同步校正標註框座標， 套用在 style/remove（有真實標註框）上會讓框位置跟物體對不上。 目前只在 neg_t2i（背景圖、無標註框）上啟用。
魚眼的畸變強度、OSD 文字格式/位置、暈影強弱都應該對照實際那幾支攝影機的真實錄影調整—— 如果現場的半球攝影機畸變沒那麼強、或 NVR 根本沒有疊時間戳記，照搬這裡的預設值反而會讓合成資料 偏離真實分佈。這三個開關預設都是關閉（p_fisheye/p_vignette/p_osd 預設 0），不影響既有的 pipeline.yaml/smoke.yaml 設定。

7.1　物件插入：比單純 inpainting 更進階的做法

方法時間重點對我們的意義
AnyDoorCVPR 2024 零樣本「物件傳送」：用參考物件的身份特徵 + 目標場景的細節特徵合成，不需要針對每個物件重新訓練。 在 VisDrone 上測試車輛插入，bus 類別在 10x 擴增下有明顯提升。 比我們現在 05 步驟用的 FLUX.1-Fill 遮罩插入更適合規模化，可評估換用。
ODGEN（arXiv 2405.15199）2024 針對領域資料微調擴散模型 + 每物件文字/視覺提示，YOLO 系偵測器 mAP@.50:.95 最高 +25.3% ——目前找到最強的量化結果，但需要針對領域資料微調生成模型，成本不低。 如果 A5（插入）效果不夠，這是進一步加碼的方向，但先把現有流程跑過一輪再考慮值不值得。
SpotLight（arXiv 2411.18665）/ DiffusionHarmonizer（arXiv 2602.24096）2024–2026 專門解決「插入物件後陰影/光照對不上背景」的問題——這正是遮罩式 inpainting 插入最容易穿幫的地方。 值得之後評估 如果 08 人工抽查發現插入物件的陰影對不上，這是對應的解法方向。
深挖後的具體結論：
  • AnyDoor 官方 repo（ali-vilab/AnyDoor）有釋出程式碼/checkpoint，介面跟我們 05 步驟現在用的 FLUX.1-Fill幾乎一樣（參考物件圖+遮罩、目標位置遮罩）——真要換， 介面不用大改，但授權沒有查到明確 LICENSE，而且依賴的 DINOv2 本身歷史上帶非商用限制， 商用前務必自己查清楚授權，不要假設能直接用在公司內部產線。
  • ODGEN 沒有釋出程式碼，而且它的 +25.3% 提升是建立在「針對目標領域資料微調擴散模型」之上 ——這一步本身就需要真實的目標領域影像，跟我們「不能蒐集新資料」的前提互相矛盾， 對我們來說實質上不可行，不只是成本高而已。
  • SpotLight 沒有找到可執行的程式碼（論文的評估資料集也還在等釋出）。但有現成可以今天直接跑的替代品： ZHKKKe/Harmonizer（ECCV 2022，GitHub 有code+權重）和 WindVChen/INR-Harmonization （TCSVT 2023）都是推論即用的影像融合（harmonization）網路，可以接在 FLUX.1-Fill 貼上物件之後當後處理， 專門修補「貼上去的感覺」。

7.1b　實際裝起來試跑：Harmonizer

把 ZHKKKe/Harmonizer clone 下來（放在 ~/.cache/repos/Harmonizer，刻意不放進 本專案 repo——下面會說明為什麼）、裝好 kornia/opencv-python-headless/tqdm、 下載官方預訓練權重（19MB，CPU 可跑，單張 <1 秒），patch 了一行 torch.load 讓它在沒有 GPU 的環境也能載入（原始 checkpoint 是存成 CUDA tensor，純 CPU 機器預設會報錯）。

裝起來之後第一件事就發現：Harmonizer 本身的授權是 CC BY-NC-SA 4.0 ——一樣是非商用。也就是說上面 7.1 節講的「現成可以直接用」要修正：可以直接跑起來驗證效果， 但不能直接用在公司商業產線上，跟 FLUX.1 Kontext 的授權問題是同一類坑。這點我自己在推薦的時候 也漏講了，寫這裡更正。

結論：技術上可行、效果看得出來，但授權排除了它當正式方案；如果真的要走這條路， 要嘛找商用授權的替代品（WindVChen/INR-Harmonization 的授權還沒查證，需要之後再確認）， 要嘛跟作者談商用授權，要嘛接受只在內部實驗階段用、正式產線上拿掉這一步。

7.2　生成資料的品質過濾：不只是單一 teacher 偵測器

7.3　監控/CCTV 領域專屬的合成資料研究

  • RGB→熱像/紅外合成（SPIE 2024、IEEE T-ASE 2025）：確認「夜視紅外合成」是跟我們現在做的 「RGB 風格轉換模擬夜視」不同的獨立研究路線，用 GAN/擴散直接生成熱像而非在可見光上套濾鏡， 夜間偵測效果更好，但需要熱像教師模型/資料，成本高很多。
  • 魚眼/半球攝影機專屬的合成資料研究：偏薄弱，沒找到 2025 年的 直接後繼研究，只有舊的 MOTSynth/DummyNet 這類行人監控合成資料基準。
  • H.264/H.265 壓縮痕跡模擬（相對於我們目前用的 JPEG 壓縮）：沒找到專文， 目前看起來是個開放的小缺口，JPEG 近似應該夠用但不是最精確的。

7.4　編輯模型版圖（2025 下半年）

FLUX.1 Kontext（Black Forest Labs，arXiv 2506.15742，2025年5月）是 Qwen-Image-Edit 之外另一個 主流選項，官方自建的 KontextBench 聲稱在局部編輯/角色保持上領先。但沒有找到獨立、可查證的 Qwen-Image-Edit vs FLUX.1 Kontext 正面對比——目前選用 Qwen-Image-Edit-2509 是合理選擇， 但文獻上還無法證明它比 FLUX.1 Kontext 更適合我們的用途，值得之後實測比較（尤其是物件移除的乾淨度）。 未證實：網路上有 blog 引用 Qwen-Image-Edit 在 GEdit-Bench 分數與 GPT-Image-1 相近，但評分用的 judge 模型不同、不能直接比較，Qwen-Image-Edit-2511 也還沒有公開的基準數據。

深挖後發現一個重要的授權問題：開源權重版 FLUX.1 Kontext [dev] 是 Black Forest Labs 的 Non-Commercial License，只有 schnell（沒有編輯能力的那個變體）是 Apache-2.0。也就是說 自架 FLUX.1 Kontext [dev] 用在公司內部的半導體廠產線上，嚴格來說需要跟 BFL 另外簽商用授權， 不是下載權重就能直接商用。唯一找到的一篇系統化多模型評測（arXiv 2606.15570）把「物件移除」列為 所有受測模型共同的最難項目，不是 Kontext 特別弱——所以就算之後要比較，也不該預期任何一個模型 能把物件移除做到完美。目前選用 Qwen-Image-Edit-2509（其授權見其官方頁面，一般開源釋出的 Qwen 模型 多為 Apache-2.0 類寬鬆授權）在商用前提下反而是更穩妥的預設選擇，除非確認 BFL 授權條件可接受。

7.5　實驗驗證的嚴謹度

  • 業界案例確認：合成資料的效果不是單調的——某車輛偵測案例顯示，真實資料只有 5% 時加合成資料讓 recall 翻倍以上，但真實資料已經 100% 時再加合成資料反而讓 recall 下降（模型變保守）。 這直接印證我們 A0–A5 分組對照實驗的設計是對的——效果因資料組合而異，不能只看一個全域的「有效/無效」結論。
  • 另一篇 2026 的煙霧偵測論文指出合成驗證集看起來會「異常地簡單/可靠」，必須用真實保留資料驗證—— 這正是我們要求 deploy_eval/deploy_bg 必須是真實畫面、不能用合成資料代替的理由。
  • 沒有找到比我們目前用的「paired bootstrap 信賴區間」更嚴謹的統計做法——我們目前的驗證嚴謹度不落後於一般常見做法。

7.6　半導體廠/無塵室/倉儲專屬的監控合成資料

調查確認：幾乎沒有專門針對半導體廠/無塵室/辦公室 CCTV 情境的公開研究（只有晶圓圖、TEM 影像生成這類 「半導體量測」的生成研究，跟「監控畫面」是完全不同的題目；另有車站/機場全向攝影機行人偵測的合成資料研究， 場景也不是廠房）。換句話說，第 6 節的無塵衣/鋼瓶混淆物清單是原創的領域調整，不是在重現某篇已發表的做法 ——沒有現成的論文可以照抄，這部分只能靠對照真實誤判案例持續調整。

9.尚未完成 / 下一步

16 個步驟的程式碼路徑現在都至少跑過一次（02/06/07/09 用真實的 sd-turbo+YOLOv8n 跑過， 03/04/05/08/10–16 用假資料+mock 驗證過邏輯，見第 6.4 節），而且生成端目前最好的也只是品質較弱的 sd-turbo 代打。距離真正能做出可行性結論，還缺：

  • 正式生成品質：需要在有 GPU、有網路的機器上跑 offline/prepare_bundle.sh， 下載 Qwen-Image、Qwen-Image-Edit-2509、Lightning LoRA、RF-DETR-Large 等權重，打包後搬進隔離 GPU 環境。
